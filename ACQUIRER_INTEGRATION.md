# Подключение RUB → USD₮ эквайринга

## Сейчас готово

Sandbox API принимает авторизованный запрос `POST /v1/purchases`:

```json
{"amount_rub_minor": 250000}
```

Передаётся заголовок `Idempotency-Key`; сумма задаётся в копейках (`250000` = 2 500 ₽). В локальном режиме ответ создаёт тестовый `purchase_id`, но `checkout_url` равен `null`: реальный эквайринг ещё не выбран и счёт у него не создаётся. Production endpoint отвечает `503`.

После тестового invoice можно прислать нормализованный callback в `POST /internal/webhooks/acquirer`:

```json
{
  "event_id": "provider-unique-event-id",
  "purchase_id": "internal-purchase-id",
  "provider_invoice_id": "provider-invoice-id",
  "status": "settled",
  "paid_rub_minor": 250000,
  "credited_usdt_minor": 12340000
}
```

Локальная песочница проверяет HMAC-SHA-256 заголовка `X-Acquirer-Signature` от `timestamp + "." + raw_body`, время из `X-Acquirer-Timestamp` (окно 5 минут), наличие invoice, статус `settled`, совпадение оплаченной RUB-суммы, уникальность event ID и не повторяет проводку. `credited_usdt_minor` — фактический чистый USD₮ к зачислению после курса и удержаний эквайера. Это **sandbox contract**, а не обещание, что так подписывает callback ваш провайдер.

## Как будет выглядеть реальное подключение

1. API создаёт purchase intent, привязывает его к прошедшему серверную проверку Telegram-пользователю и сохраняет RUB сумму и idempotency key.
2. Адаптер эквайера запрашивает quote/invoice. Сервер сохраняет provider invoice ID, срок действия курса, quote ID, RUB gross, все комиссии и минимальный net USD₮. Клиент получает только checkout URL и показанную котировку.
3. Эквайер принимает рубли и конвертирует средства по своему договору. Webhook сигнализирует о событии, но API перепроверяет его подпись, timestamp/replay и состояние invoice через server-to-server API. Не зачислять по редиректу браузера или статусу, пришедшему от клиента.
4. Прежде чем увеличить внутренний ledger, сервер подтверждает фактическое получение расчётного USD₮ у custody/treasury settlement account или доверяет подтверждённому settlement record эквайера по согласованной схеме. Затем одной транзакцией БД создаёт сбалансированные проводки, помечает invoice credited и записывает provider event. Любая ошибка оставляет invoice в ожидании/ручной проверке.
5. Повторы webhook безопасны по provider event ID и invoice ID. Сумма, пользователь, сетевой токен или реквизиты не берутся из полей, которые клиент может подменить.

Для реального callback формат подписи, названия статусов и поля будут преобразованы в этот внутренний протокол отдельным адаптером. Settlement-finality, частичная оплата, переплата, chargeback, возврат RUB, отмена после курса и задержка выплаты должны соответствовать реальному договору эквайера; сейчас они не реализованы и должны оставаться fail-closed.

## Что нужно получить от владельца проекта

Пожалуйста, пришлите несекретные материалы/ответы:

1. Название эквайера и ссылки/файлы его **официальной API-документации**, включая sandbox.
2. Какие продукты по договору подключены: RUB СБП/карта, AML/KYC, покупка/обмен криптоактива, крипторасчёт, payout. Эквайринг может принимать RUB и считать курс, но это не гарантирует, что он отправляет USD₮ на наш settlement wallet или разрешает зачислять клиентам внутреннее обязательство.
3. Список supported chains/token contracts (TRON TRC-20, BSC BEP-20, Ethereum ERC-20, Polygon, Arbitrum), регион/лимиты/минимумы и способ получения **расчётного USD₮**: перевод на корпоративный кошелёк, custody API или только сумма к начислению.
4. Sandbox merchant ID/client ID, test mode instructions, callback retries и IP allowlist. Сами секреты API и webhook secret в чат не отправляйте; их безопасно добавить напрямую в secret manager/deployment environment после выбора hosting.
5. Примеры успешных/ожидающих/неуспешных webhook и API-ответов (секреты и персональные данные удалить), алгоритм подписи, API endpoint для серверной проверки статуса invoice, ключи ротации и idempotency semantics.
6. Курс: гарантируется ли на время оплаты; в какой момент фиксируется; RUB gross, комиссия эквайера, spread, криптосумма gross/net, округление и кто покрывает недостачу при изменении курса.
7. Правила возврата/chargeback, частичной оплаты и повторной оплаты, сроки финального settlement и юридические документы эквайера, разрешающие именно эту схему для российского оператора/клиентской базы.

## Что нужно для развёртывания

- Выбранный hosting/provider и созданная учётная запись с нужной российской зоной размещения БД; DNS-домен и TLS сертификат для API/webhook. Для одного репозитория это может быть Docker-host/managed container + managed PostgreSQL, но конкретный сервис нужно выбрать с учётом правового допуска и локализации данных.
- Реквизиты юридического лица/оператора, договор эквайера и заключение по модели внутреннего баланса/вывода в РФ. Уточнить, кто является продавцом/обменником/кастодианом и кто отвечает за KYC/AML.
- Telegram bot token и зарегистрированный Mini App URL.
- Custody/HSM/MPC аккаунт и отдельные test/prod wallets; KMS роль, не экспортируемый ключ и лимиты. Private key/seed-фраза в приложение или чат не передаются.
- Sandbox RPC/indexer и test tokens для сверки settlement. Для production RPC нужны SLA, лимиты, независимая сверка и мониторинг.
- Лимиты, политика комиссий (отдельно курс, комиссия эквайера, наша комиссия и кроссчейн/network costs), SLA, поддержка/эскалация, мониторинг/alerts, бэкапы и восстановление.

После получения документации подключается sandbox adapter, затем проверяются API/webhook на тестовом merchant, дубликаты/неверные подписи/переплата/отказ/таймаут, реальный testnet settlement с custody-провайдером, reconciliation и только затем deployment. Production включается отдельно после legal и security review; сейчас backend блокирует этот режим.
